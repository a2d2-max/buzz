# huddle-stt-bench — 한국어 STT 엔진 비교 측정

허들 회의록에 쓸 받아쓰기(STT) 엔진을 같은 오디오, 같은 채점 규칙으로 비교한다.
오디오 파일과 사람이 바로잡은 정답 글을 넣으면 엔진마다 CER, RTF, 처리 시간, 실패 수, 예상 비용을 낸다.

| 엔진 이름 | 무엇 | 어디서 | 필요한 것 |
|---|---|---|---|
| `chirp3` (`chirp3:eu`) | Google Cloud Speech-to-Text v2, 모델 `chirp_3`, `ko-KR`, 지역 `us`(기본) 또는 `eu` | Google 멀티리전 (**음성이 한국 밖으로 나감**) | GCP 자격(ADC 또는 gcloud 계정), 프로젝트 `a2d2-lab` |
| `qwen3-asr` | `sherpa-onnx-qwen3-asr-0.6B-int8-2026-03-25`, `language=Korean` | 이 컴퓨터 CPU | 없음 (모델 자동 받기, 약 0.9GB) |
| `sense-voice` | `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17`, `language=ko`, `use_itn=True` | 이 컴퓨터 CPU | 없음 (모델 자동 받기, 약 0.2GB) |

로컬 엔진은 `sherpa-onnx>=1.13.8` 을 쓴다. 1.13.7 은 조용한 구간에서 헛소리를 내고, 1.13.8 에서 동시 실행 버그가 고쳐졌다.

## 설치

[uv](https://docs.astral.sh/uv/) 가 있으면 된다. 이 폴더에서:

```bash
uv sync
uv run pytest -q          # 채점 규칙, chirp 재시도, qwen3 토큰 계산 시험(네트워크·모델 없이 돈다)
```

## 쓰는 법

```bash
# 1) FLEURS 한국어 test 에서 문장 30개를 받아 manifest 를 만든다 (.cache/fleurs-ko-test/)
uv run huddle-stt-bench fetch-fleurs --n 30

# 2) 엔진들을 돌린다. 결과는 .cache/results/<시각>-<manifest 폴더 이름>.json / .md (저장소에 안 들어감)
uv run huddle-stt-bench run --manifest .cache/fleurs-ko-test/manifest.jsonl --gcp-auth gcloud

# FLEURS 결과를 저장소에 남길 때만 --out results 를 직접 준다
uv run huddle-stt-bench run --manifest .cache/fleurs-ko-test/manifest.jsonl --gcp-auth gcloud --out results

# 채점 규칙을 바꾼 뒤, 이미 있는 결과를 다시 센다 (받아쓰기는 다시 안 돌림, 요금 없음)
uv run huddle-stt-bench rescore results/<결과>.json

# 긴 트랙을 Chirp 3 에 보내는 방식 비교 (아래 "긴 트랙에서 Chirp 3 에 보내는 방식 비교")
uv run huddle-stt-bench long-compare --gcp-auth gcloud --dry-run
```

주요 옵션 (`uv run huddle-stt-bench run --help` 로 전부 볼 수 있다):

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `--engines` | `chirp3,qwen3-asr,sense-voice` | 돌릴 엔진. 인증이 없거나 API 가 꺼진 엔진은 까닭을 적고 건너뛰고, 나머지는 계속 돈다 |
| `--out` | `<cache-dir>/results` | 결과 폴더. 기본값은 저장소에 안 들어간다 |
| `--gcp-auth` | `adc` | chirp3 인증. `adc` = ADC 또는 `GOOGLE_APPLICATION_CREDENTIALS` 서비스 계정, `gcloud` = gcloud 에 지금 로그인한 계정(`gcloud auth print-access-token`) |
| `--gcp-project` | `a2d2-lab` | chirp3 를 부를 프로젝트(요금도 여기로 붙는다) |
| `--num-threads` | 4 | 로컬 엔진 스레드 수. 결과 파일에 같이 남는다 |
| `--concurrency` | 4 | 원격 엔진 동시 요청 수 (로컬 엔진은 늘 하나씩) |
| `--long-audio-sec` | 30 | 이보다 긴 오디오는 silero VAD 로 말소리 조각(20초까지)으로 잘라 넣는다. qwen3-asr 는 토큰 예산을 따로 재서 더 짧아도 자른다(아래) |
| `--limit` | 없음 | 앞에서 몇 개만 (시험용) |

### 결과 파일과 저장소

결과 JSON 에는 정답 글과 받아쓴 글이 다 들어간다. 회의 녹음 결과가 커밋되면 회의 내용이 저장소에 남는다. 그래서 두 겹으로 막는다:

- `--out` 기본값이 `.cache/results/` 다(`.cache/` 는 `.gitignore`).
- `results/.gitignore` 가 `*` 를 무시하고 `.gitignore` 와 이름에 `-fleurs-` 가 든 파일만 들인다. `--out results` 로 회의 결과를 써도 git 이 무시한다.

### manifest 형식 (JSONL)

한 줄에 파일 하나:

```json
{"id": "meeting-0001", "audio": "audio/0001.wav", "text": "사람이 바로잡은 정답 글"}
```

- `audio` 가 상대 경로면 manifest 파일이 있는 폴더 기준이다.
- 오디오는 wav, flac, ogg, mp3 (soundfile 이 읽는 형식). 모든 엔진이 같은 입력을 받도록, 읽어서 모노로 섞은 뒤 넣는다. chirp3 에는 그 모노 소리를 16비트 PCM WAV 로 만들어 보낸다. m4a 같은 것은 먼저 바꾼다:
  `ffmpeg -i in.m4a -ac 1 -ar 16000 -c:a pcm_s16le out.wav`

### chirp3 인증과 요청

액세스 토큰은 화면, 로그, 결과 파일 어디에도 찍지 않는다. 실행할 때 메모리로만 쓴다.
API 가 실패하면 HTTP 상태와 오류 코드만 남긴다(예: `HTTP 403 PERMISSION_DENIED IAM_PERMISSION_DENIED`). 오류 본문 글은 남기지 않는다.

- 시작할 때 돈이 안 드는 recognizer 목록 조회로 API 상태와 권한을 먼저 본다.
  - API 가 꺼져 있으면 `API 꺼짐` 으로 건너뛴다. 켜는 것은 이 도구가 하지 않는다.
  - 권한이 없으면 `준비 실패 … IAM_PERMISSION_DENIED` 로 건너뛴다.
- 사용자 자격은 쿼터 프로젝트가 비어 있을 수 있어서, 요청에 `x-goog-user-project: <--gcp-project>` 를 붙인다.
- 지역은 `us`, `eu` 만 받는다(Chirp 3 이 GA 인 멀티리전). 다른 값은 시작 전에 거절한다.
- 재시도: 429, 500, 502, 503, 504, 연결 끊김, 타임아웃이면 1초, 2초, 4초 쉬고 세 번까지 다시 보낸다. 다른 오류(400, 403 등)는 바로 실패로 센다. 다시 보낸 횟수는 결과에 `retries` 로 남고 표 아래에 경고가 붙는다.
- 데이터 로깅: 요청에 데이터 로깅을 켜는 값은 넣지 않는다. 데이터 로깅은 프로젝트 단위로 콘솔(Cloud Speech API → Data logging 탭)에서 켜고 끄는 설정이다. API 로는 그 상태를 확인하지 못했다.

> 2026-10-12 이 맥에서: ADC(`application_default_credentials.json`)는 기본 프로젝트가 `a2d2-ai` 인 다른 계정으로 만들어져 있었다. 그 계정에는 a2d2-lab 의 `speech.recognizers.list` 권한이 없었다(403).
> 그래서 측정은 gcloud 에 로그인한 계정으로 돌렸다(`--gcp-auth gcloud`). 권한은 건드리지 않았다.

### 받는 파일 확인

모델과 데이터는 아래에 박아 둔 sha256 과 맞을 때만 쓴다. 임시 폴더에 받거나 풀고, 맞으면 제자리로 옮긴다. 안 맞으면 지우고 멈춘다.

| 파일 | sha256 을 맞춰 본 곳 |
|---|---|
| qwen3-asr, sense-voice 모델 아카이브, `silero_vad.onnx` | GitHub 릴리스 API(`releases/tags/asr-models`)의 asset digest |
| FLEURS `ko_kr/{test,dev}.tsv` (정답 글) | Hugging Face git blob 해시와 맞는 것을 확인한 뒤 잰 sha256 |
| FLEURS `ko_kr/audio/{test,dev}.tar.gz` | Hugging Face LFS 가 알려 준 sha256 |

## 무엇을 재나

| 칸 | 뜻 |
|---|---|
| CER | 유니코드 NFKC → 폭 없는 글자(범주 Cf) 제거 → 문장부호(범주 P\*) 제거 → 공백 모두 제거 → 글자 단위 편집 거리 ÷ 정답 글자 수 |
| 공백 포함 CER | 같지만 공백은 지우지 않고 연속 공백만 하나로 줄인다. 띄어쓰기 차이도 오류로 센다 |
| 모든 엔진 성공 CER | 돌린 엔진이 모두 성공한 파일만 모아 센 CER. 엔진마다 실패한 파일이 다를 때 같은 파일로 비교하려고 낸다 |
| 참고: 괄호 뺀 CER | 정답에서 괄호 안 글을 지우고 센 CER(공백 뺌). FLEURS 정답에는 읽지 않은 괄호 병기가 있어서 참고로 같이 낸다 |
| RTF | 처리 시간 ÷ 오디오 길이. 1보다 작으면 실시간보다 빠르다 |
| 총 처리 시간 | 파일마다 걸린 시간의 합(초). 실패한 파일도 들어간다 |
| 준비 시간 | 로컬은 모델 올리기, chirp3 는 인증과 API 확인에 든 시간 |
| 실패 | 오류로 끝난 파일 수 |
| 예상 비용 | chirp3 는 Google 이 응답에 적어 준 초(`totalBilledDuration`)로, 없으면 오디오 길이로 계산한다. 1시간 기준 비용도 같이 낸다 |

- CER 칸은 `비율 (편집 거리 합/정답 글자 수 합)` 으로 찍는다. 여러 파일을 합친 CER 은 편집 거리 합 ÷ 정답 글자 수 합이다. **성공한 파일만** 센다.
- 문장부호를 지울 때 예외 둘:
  - `%` 는 남긴다. "퍼센트"로 읽히는 낱말이라, 지우면 "3%" 와 "3" 이 같아진다.
  - 숫자 사이 `.` 는 소수점이라 남긴다("75.6" 이 "756" 이 되지 않게). 숫자 사이 `,`(천 단위)는 다른 문장부호처럼 지운다("1,000" = "1000").
- **숫자 정리 차이가 CER 에 섞인다.** "세 시" 와 "3시" 를 같은 것으로 바꾸지 않는다. 엔진이 숫자를 글로 쓰든 아라비아 숫자로 쓰든, 정답과 다르면 오류로 센다. 영문 대소문자도 그대로 둔다.
- chirp3 의 처리 시간에는 한국에서 us 까지 업로드와 네트워크 왕복이 다 들어간다. 엔진 자체 속도가 아니다. 동시 요청 수를 늘리면 전체 걸린 시간(결과 JSON 의 `wall_sec`)은 줄지만 RTF 는 그대로다.
- chirp3 설정: `model=chirp_3`, `languageCodes=["ko-KR"]`, `autoDecodingConfig={}`, `features.enableAutomaticPunctuation=true`. recognizer 는 따로 만들지 않고 기본 recognizer `projects/<프로젝트>/locations/<지역>/recognizers/_` 를 쓴다(Chirp 3 문서 예제와 같음). 주소는 `https://<지역>-speech.googleapis.com/v2/...:recognize`. 결과의 `results[].alternatives[0].transcript` 를 공백으로 잇는다.
- 결과 표 아래 경고: 어느 엔진이든 파일을 VAD 조각으로 잘라 넣었으면(결과의 `pieces` > 1) 그 수를 적는다. qwen3-asr 가 토큰 한도에 닿았거나, chirp3 가 요청을 다시 보냈어도 적는다.

### 비용 계산 근거 (2026-10-12)

- Chirp 3: Speech-to-Text V2 Recognition, 월 0~50만 분 **$0.016/분**(데이터 로깅 안 켬. Cloud Billing Catalog 값이고 [가격 페이지](https://cloud.google.com/speech-to-text/pricing)와 같다).
  - 가격 페이지에 "요청마다 1초 단위로 올림" 이라고 적혀 있다. Google 이 매긴 초가 응답에 있으면 그 초로 계산하고, 없으면 파일마다 `올림(길이 초) ÷ 60 × $0.016` 으로 어림한다.
  - 첫 측정에서 Google 이 매긴 초 합(407초)과 어림(파일 30개, 407초)이 같았다.
  - 같은 모델을 BatchRecognize 의 Dynamic Batch(24시간 안에 처리)로 돌리면 **$0.003/분**(1시간 $0.18)이다.
  - 가격 페이지의 Standard 모델 목록에는 "chirp (V2 only)" 로만 적혀 있고 `chirp_3` 이라는 이름은 따로 없다.
- 로컬 엔진은 0 으로 적는다(전기, 서버 값은 넣지 않았다).

## 첫 측정 (2026-10-12, FLEURS 한국어 test 30개)

결과 파일: `results/20261012-130223-fleurs-ko-test.json`, `.md`.
돌린 곳: Apple M4 Max(논리 코어 16개), 로컬 엔진 스레드 4개, macOS 26.2, Python 3.12.12, sherpa-onnx 1.13.8.
Chirp 3 은 `us` 멀티리전, 인증 gcloud 계정, 동시 요청 4개. 오디오 30개 합계 393.7초(파일 하나 4.7~25.8초).

|---|---|---|---|---|---|---|---|---|---|---|
| chirp_3@us | 30/30 | 4.69% (70/1491) | 4.80% (93/1938) | 4.69% (70/1491) | 3.26% (46/1410) | 0.345 | 136.0초 | 0 | $0.1085 (매긴 407초) | $0.96 |
| qwen3-asr | 30/30 | 7.24% (108/1491) | 7.02% (136/1938) | 7.24% (108/1491) | 4.18% (59/1410) | 0.070 | 27.6초 | 0 | 0 (로컬) | 0 (로컬) |
| sense-voice | 30/30 | 9.12% (136/1491) | 9.13% (177/1938) | 9.12% (136/1491) | 6.10% (86/1410) | 0.010 | 4.0초 | 0 | 0 (로컬) | 0 (로컬) |

- chirp_3 은 us 지역에서 처리됐다. 음성이 한국 밖으로 나갔다.
- 같은 측정을 세 번 돌렸을 때 세 엔진 모두 받아쓴 글 30개가 한 번도 다르지 않았다(Chirp 3 포함). RTF 만 시간 재기 오차만큼 흔들렸다(qwen3-asr 4스레드는 여러 번 돌려 0.070~0.072).
- **다시 채점함(2026-10-12):** 위 숫자는 받아쓰기를 다시 돌리지 않고 지금 채점 규칙으로 다시 센 값이다(`rescore`).
  - 처음 규칙(소수점·`%` 도 지움)으로는 4.57% / 7.12% / 9.00% 였다.
  - 바뀐 파일은 하나다. 정답 `…문서(75.6 cm x 62.2 cm)는…` 의 소수점 두 개가 이제 남아서, 정답이 2글자 늘고 오류가 2 늘었다. 세 엔진 다 이 괄호 글을 받아쓰지 않았다.
  - 30개 정답·받아쓴 글에 폭 없는 글자와 `%` 는 없었다. 괄호 뺀 CER 은 그대로다.

### Qwen3-ASR 이 1시간 회의를 몇 분에 끝내나

같은 30개를 스레드 수만 바꿔 다시 돌렸다(이 맥, Apple M4 Max). 스레드 1·2·8개 결과의 받아쓴 글은 본 측정(4스레드)과 30개 모두 같고, 속도만 달라진다.
1시간 회의 처리 시간 = RTF × 60분이다(한 번에 회의 하나, 모델 올리는 1.3초는 뺌).

| 스레드 | qwen3-asr RTF | 1시간 회의 | sense-voice RTF | 1시간 회의 |
|---|---|---|---|---|
| 1 | 0.157 | 약 9.4분 | 0.030 | 약 1.8분 |
| 2 | 0.102 | 약 6.1분 | 0.017 | 약 1.0분 |
| 4 | 0.070 | 약 4.2분 | 0.010 | 약 0.6분 |
| 8 | 0.057 | 약 3.4분 | 0.007 | 약 0.4분 |

- 4스레드 값은 본 측정, 1·2·8스레드 값은 `.cache/threads-<N>/` 에 있다.
- 108초짜리 긴 파일(아래)을 VAD 로 잘라 넣었을 때도 qwen3-asr RTF 는 0.071~0.072(4스레드)로 짧은 파일과 비슷했다.
- **서버 CPU 에서는 다르다.** M4 Max 코어는 흔한 클라우드 vCPU 보다 빠른 편이라, 서버에서는 이 표보다 느릴 수 있다. 얼마나 느린지는 서버에서 재 보기 전에는 알 수 없다. 서버에서 `--engines qwen3-asr --num-threads <N>` 으로 같은 30개를 돌리면 바로 비교된다.

### 이 숫자를 읽을 때 알아 둘 것

- **FLEURS 정답에 읽지 않은 괄호 글이 있다.** 30개 중 4개 정답에 `(United States Geological Survey)`, `(75.6 cm x 62.2 cm)` 같은 괄호 병기가 있다. 읽은 사람이 소리 내지 않아서 세 엔진 다 받아쓰지 않았고, 그대로 오류로 잡혔다. 측정 규칙은 바꾸지 않았고, 괄호 뺀 CER 은 참고 칸으로만 낸다.
- **qwen3-asr 는 입력이 아주 조금만 바뀌어도 결과 글이 바뀐다.** 같은 파일을 여러 번 돌리면 결과는 늘 같다. 그런데 소리 크기를 0.003% 줄이면(32767/32768배) 30개 중 16개 결과 글이 달라지고 CER 이 7.58%(113/1491) 가 된다. sense-voice 는 같은 변화에 3개가 달라지고 9.32%(139/1491) 가 된다(둘 다 지금 채점 규칙). 이 30개로는 0.3%p 안팎 차이는 의미 없다고 봐야 한다. chirp_3 으로는 이 시험을 하지 않았다.
- sense-voice 는 `use_itn=True` 인데도 한국어 숫자를 "천 구백 육십 칠 년" 처럼 글로 쓴 적이 있다. 이런 차이도 CER 에 섞여 있다.

## 긴 녹음 자르기 (회의록 작업기 설계에 쓸 것)

회의 녹음은 몇십 분짜리라 어떤 엔진에도 통째로 넣을 수 없다. 그래서 이 도구는 긴 오디오를 잘라서 넣는다. 작업기를 만들 때 알아야 할 것:

- **Qwen3-ASR 은 20초 안팎으로 잘라 넣어야 한다.**
  - 이 모델(sherpa-onnx int8 내보내기)은 KV 캐시 한도가 512토큰이다. 이 한도 안에 프롬프트, 소리, 받아쓴 글이 다 들어가야 한다.
  - 프롬프트는 18토큰이다(`language=Korean` 일 때 sherpa-onnx 로그 "before=9 after=9").
  - 소리는 1초에 13토큰이다. sherpa-onnx 가 특징을 1초(100프레임) 덩어리로 나누고, 덩어리마다 stride 2 로 세 번 줄인다(`offline-recognizer-qwen3-asr-impl.cc` 의 `FeatToAudioTokensLen`, `kQwen3ChunkSize = 100`). 이 계산으로 108.3초는 1408토큰인데, 실제 잘림 로그의 숫자와 같았다. 20초는 소리만 260토큰, 30초는 390토큰이다.
  - 받아쓴 글은 FLEURS 30개에서 소리 1초에 2.12~5.77토큰(가운데 3.08)이었다. 가장 빠듯한 25.8초 파일이 18 + 335 + 93 = 446토큰이었다.
  - 한도를 넘으면 sherpa-onnx 는 오류를 내지 않는다. 소리가 길면 표준 에러에 `Truncating audio placeholders` 를 찍고 소리를 잘라 버린다(108초 통째로: 1408토큰 중 494만 남고 CER 99.73%). 글이 길면 아무 말 없이 글을 끊는다.
- **이 도구의 qwen3-asr 처리**
  1. 미리 재기: 18 + 소리 토큰 + 글 예상(소리 1초에 6토큰, 잰 최대 5.77 을 올림)이 512 를 넘거나 `--long-audio-sec` 보다 길면 처음부터 자른다. 이 셈으로는 25.99초까지 한 번에 넣는다. FLEURS 30개는 하나도 안 잘린다.
  2. 끝나고 다시 재기: 실제로 나온 글 토큰 수로 18 + 소리 + 글이 한도에 닿았는지 본다. 닿았으면 잘라서 다시 돌리고(`resplit_after_cap`), 잘라도 닿으면 `capped_pieces` 로 남긴다. 둘 다 표 아래 경고에 나온다.
  3. 시험: 글 예상을 일부러 0으로 두고 36.1초 파일(소리 469토큰)을 한 번에 넣었더니, 한도에 닿은 것을 알아채고 2조각으로 다시 돌려 글이 끝까지 나왔다.
  - 리뷰에서는 「qwen3 는 20초로 고정」을 제안했는데, 위처럼 토큰 예산으로 정했다. 20초로 고정하면 20.8초·25.8초 FLEURS 파일이 20초 + 짧은 꼬리로 잘려, 짧은 조각에서 없는 말을 지어내던 문제(아래)를 새로 부를 수 있어서다. 끝나고 다시 재기가 잘림을 정확히 잡으니, 미리 재기는 덜 자르는 쪽으로 뒀다.
- **자르는 법 (`engines.vad_pieces`)**
  1. silero VAD 로 말소리 구간을 찾는다(쉼 0.25초 이상이면 끊고, 한 구간은 최대 20초).
  2. 구간 앞뒤로 0.2초 여유를 둔다.
  3. 이어진 구간을 20초가 넘지 않게 합친다.
- **잘게 자르면 안 된다.** VAD 구간을 합치지 않고 그대로(0.7~11.8초) 넣으면 짧은 조각에서 qwen3-asr 가 없는 말을 지어냈다("그러나, 그의 상황은 더욱 악화되었다."). 조각 앞머리 소리도 잘렸다.
- **엔진마다 맞는 조각이 다르다.** sense-voice 는 합친 20초 조각에서 낱말을 통째로 빠뜨렸다("수치를 밝히지", "코차모 밸리"). chirp_3 은 조각 뒷부분 말을 버렸다(아래).

### 긴 녹음 시험 (108.3초 파일 하나)

FLEURS 앞 8개를 0.7초 무음을 두고 이어 붙였다(`.cache/longtest/`, 정답 377글자. 이 8개 정답에는 소수점이 없어서 채점 규칙을 바꿔도 숫자가 같다).

| 넣는 방법 | chirp_3@us | qwen3-asr | sense-voice |
|---|---|---|---|
| 같은 8문장을 하나씩 (본 측정에서) | 1.33% (5/377) | 7.43% (28/377) | 8.75% (33/377) |
| 통째로 하나 | 못 함 (Recognize 는 1분 미만) | 99.73% (376/377) | 35.81% (135/377) |

- **chirp_3 은 합친 조각 7개 중 2개에서 조각 뒷부분 말을 버렸다.**
  - 조각 하나에 결과가 하나씩 왔는데, 0.7초 쉼 뒤에 오는 「건조한 두 분말을 함께 휘저은 후에」와 「일반적으로 두 가지 행동은 … 나타날 수 있습니다.」가 없었다.
  - 같은 조각을 qwen3-asr 는 받아썼으니 소리는 조각 안에 있었다.
  - 쉼 자리의 완전 무음(0 값)을 작은 잡음으로 바꿔도 그대로였다.
  - 조각 끝에 무음 1초를 붙이면 첫째는 살아났지만 둘째는 여전히 없었다.
  - 이 파일 하나에 맞춰 더 고치면 그 파일에만 맞춘 튜닝이 되어 멈췄다. 이 도구에서는 더 손대지 않고 경고만 남긴다.
- chirp_3 을 긴 회의로 제대로 비교하는 일(BatchRecognize 와 말 한 덩어리씩 Recognize)은 회의록 작업기에서 실제 녹음으로 한다. BatchRecognize 는 오디오를 Cloud Storage(`gs://`) 주소로만 받는다. 합성 트랙으로 먼저 잰 결과는 바로 아래에 있다.

### 긴 트랙에서 Chirp 3 에 보내는 방식 비교 (`long-compare`, 2026-10-12)

```bash
uv run huddle-stt-bench long-compare --gcp-auth gcloud            # 트랙 2개 × 4분, 방식 A·A2·B·Bw
uv run huddle-stt-bench long-compare --gcp-auth gcloud --dry-run  # 트랙과 예상 매긴 초만 (요금 없음)
```

- **트랙:** FLEURS test 문장을 성별로 나눠 사람 2명 × 4분 남짓 트랙(16kHz 모노)으로 이었다.
  - track-1: 남, 248.3초, 문장 9개. track-2: 여, 246.9초, 문장 11개.
  - 문장 사이는 0.5~3초 쉼, 트랙마다 10~30초 긴 침묵 5번(다른 사람이 말하는 동안). 시드 20261012.
  - 무음 자리에도 약 −70dBFS 바닥 잡음을 깔았다.
  - 정답 시각은 문장마다 VAD 로 찾은 말소리 시작이다. 트랙 전체를 VAD 로 다시 보면 가장 가까운 말소리 시작과 최대 0.057초 차이였다.
- **방식:**
  - A: VAD 말 덩어리(합치지 않음, 0.5초 이상 쉬면 끊음, 최대 29초, 앞뒤 0.2초 여유)를 하나씩 Recognize.
  - A′: 20초까지 합친 조각을 하나씩 Recognize(측정 도구의 지금 방식).
  - B: 트랙 전체를 `gs://a2d2-huddle-recordings/dev/stt-bench/<실행 id>/` 에 올리고 BatchRecognize. Bw 는 B 에 단어 시각을 켠 것.
- **비용 장부:** Chirp 가 매긴 초를 `.cache/long-compare/chirp-ledger.jsonl` 에 요청마다 적는다. 계획한 초가 상한(`--budget-sec`, 기본 1800초)을 넘으면 아무것도 보내지 않는다. 이번 일 합계는 1,473초(24.55분, $0.39)였다. 작은 시험 49초 + 본 측정 1,424초.
- 결과: `.cache/long-compare/20261012-134240/` (`summary.md`, `results.json`, `tracks.json`)

CER 칸은 다른 구현(rapidfuzz)으로 다시 세어 같았다. 읽는 법:

- **받아쓰기:** A 와 B 는 비슷하다(오류 72 대 77). 이 정도 차이는 표본 20문장에서 의미를 두기 어렵다.
  - CER 의 대부분은 track-1 의 괄호 병기 정답 두 문장에서 나왔다(「코차모 밸리(Cochamó Valley)」, 「미국 지질조사국(United States Geological Survey)」). A 의 track-1 오류 57개 중 53개다.
- **A′ 는 문장 하나를 통째로 놓쳤다.** track-2 「모든 남아프리카 국립공원과…」(118.9~125.3초)다. 앞 문장과 4.5초 쉼을 두고 한 조각(107.1~126.2초)으로 합쳐졌는데, Chirp 3 이 조각 뒷부분을 버렸다. 108초 시험에서 본 것과 같다. 쉼을 건너 합치는 것이 문제다.
- **시각:**
  - A·A′ 는 부호 있는 오차가 −0.26~+0.01초, 중앙값 −0.20초다. 한 문장(+0.01초)을 빼면 모두 0.14~0.26초 일찍 찍혔다. 조각 앞 여유 0.2초만큼이니, 그만큼 빼면 덩어리 위치로 문장 시작을 0.1초 안팎으로 안다.
  - B(단어 시각 끔)는 결과에 `resultEndOffset` 이 없어 시각이 하나도 없다(Chirp 3 문서: 발화 시각은 StreamingRecognize 전용).
  - Bw 는 20문장 중 17개가 0.25초 안이다. 나머지 3개는 그 문장 앞 침묵 길이(2.6, 3.3, 33.8초)만큼 일찍 찍혔다. 단어 시각이 빈틈없이 이어 붙어서, 침묵 뒤 첫 단어의 시작이 앞 단어의 끝(또는 0초)이 된다. 단어 끝 시각만 믿을 만하다.
- **처리 시간:** 이번엔 BatchRecognize 4건이 21~30초씩 걸렸다. 작은 시험에서는 같은 20초 파일 하나가 369초 걸린 적이 있어 대기가 들쭉날쭉하다. A 는 4개씩 동시에 보내 트랙 하나에 10~12초였다.
- **비용:**
  - B 는 트랙 전체(침묵 포함)에 매긴다(496초). A 는 말소리 덩어리에만 매긴다(215초, B 의 43%).
  - 사람별 트랙은 대부분 침묵이라 A 가 싸다. B 를 Dynamic Batch($0.003/분)로 돌리면 496초에 $0.025 지만 24시간 안에만 끝난다.
- **이 시험이 A 에 유리한 점:**
  - 문장 사이가 늘 0.5초 넘게 비어 있어서 VAD 덩어리가 문장과 정확히 하나씩 맞았다(9개=9문장, 11개=11문장).
  - 실제 대화는 쉼이 짧고, 말이 겹치고, 간투어가 있어서 덩어리가 문장보다 길거나 짧아진다.
  - 읽은 말(FLEURS)이고 트랙 2개·20문장뿐이다. 실제 회의 녹음으로 다시 재야 한다.

## 데이터 출처

첫 측정은 Google [FLEURS](https://huggingface.co/datasets/google/fleurs) `ko_kr` test 를 쓴다(CC-BY-4.0, Conneau et al., 2022, "FLEURS: Few-shot Learning Evaluation of Universal Representations of Speech").

- `fetch-fleurs` 는 `data/ko_kr/test.tsv` 에서 문장 번호 순으로 문장마다 녹음 하나씩 고른다. 정답 글은 `raw_transcription`(원문 표기)을 쓴다.
- 오디오 아카이브(`data/ko_kr/audio/test.tar.gz`)는 저장하지 않는다. 받으면서 필요한 파일만 임시 폴더에 뽑고, 아카이브 sha256 이 맞으면 제자리로 옮긴다.
- 원본은 32비트 float WAV 라서 16비트 PCM WAV 로 바꿔 저장한다. 차이는 16비트 한 칸 이하이고, 모든 엔진이 같은 파일을 쓴다.
